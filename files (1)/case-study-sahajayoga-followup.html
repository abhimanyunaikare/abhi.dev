The Organisation

A grassroots community with a complex coordination problem

Sahaja Yoga Pune runs regular public programmes and Pratishthan sessions that attract new seekers — people who attend an introductory event and express interest in learning more.

Before this app, the entire follow-up process lived in WhatsApp groups and shared spreadsheets. Volunteers had no clear view of who had been called, who had been assigned a mentor, or where any individual was in their journey.

The ask was simple in concept but complex in execution: build a system every volunteer could use on their phone, with each role seeing exactly what they needed — and nothing more.

The Challenge

Eight problems to solve before writing a line of code

  • 10 user roles with different data visibility — admin down to individual callers — with no overlap in what each sees by default
  • A seeker journey with 6 distinct statuses that must advance automatically based on volunteer actions, not manual updates
  • A dual seeker type (Pratishthan vs. Public Programme) with completely different checklist fields, session tracking, and assignment workflows
  • Volunteers needed fast search across thousands of records without triggering role-restricted filters designed for normal browsing
  • Bulk seeker assignment to callers and mentors — across hundreds of records — with a single tap from a coordinator's device
  • The "My Seekers" screen needed to persist history — a caller who is later demoted should still see their full past assignment list
  • Zonal isolation — each Zonal Leader should only ever see seekers from their own zone, even on search
  • Existing screens for other roles were live in production — any backend change to the main /seekers route risked breaking them

Engineering Decisions

The choices that shaped the system

🔀
Separate route for "All Seekers"
Rather than adding a flag to the existing /seekers route and risking regressions across live screens, a new /seekers/all endpoint was created with clean, role-aware logic from scratch.
🔍
Search bypasses role filters
An $isSearching flag on the backend detects when a name, mobile, or date is in the request and skips status-based role gates — letting coordinators find any seeker instantly while preserving the default scoped view.
📋
My Seekers shows full history
The my_seekers=1 flag returns every seeker ever linked to the user as caller or mentor — regardless of current status — so no assignment is ever lost from view even as seekers progress through stages.
⚡
Debounced search on device
A 500ms debounce hook prevents an API call on every keystroke. Combined with paginated responses (20 per page) and cursor-based load-more, the list stays fast even on a slow mobile connection.
🎯
Status advances automatically
When a CCT coordinator assigns a caller, the seeker's status moves from 0 → 1. When a call is logged as completed, it moves to 2. When a mentor is assigned by a Zonal Leader, it moves to 3. No manual status field for volunteers to forget.
✅
Checklist lives in its own table
Session attendance, monthly follow-ups, and activity flags are stored in a dedicated seeker_checklists table, keeping the seekers table clean and allowing filtered queries via whereHas without joins.

Build Process

How it came together

Discovery
Mapping the volunteer journey
Workshops with coordinators, callers, and zonal leaders to understand exactly what each role needed to see — and what would slow them down if they saw too much.
Backend First
Schema and API design
Database schema, migrations, and all REST endpoints designed and tested in isolation before any mobile screen was built. Role-based filtering was validated with real data from day one.
Core Screens
Seeker list, detail, and assignment
The three highest-traffic screens — list, detail view, and bulk assignment — were built and refined with volunteers testing on real devices before moving to secondary screens.
Iteration
Filter redesign and UX polish
Original filter modal used chip-based multi-selects that confused volunteers. Replaced with toggle buttons, dot selectors, and an active-filter count badge — reducing support queries significantly.
Production
Rollout and handover
Phased rollout starting with CCT coordinators, then expanding to all roles with documentation and a walkthrough session. Zero downtime migration from the existing spreadsheet system.
